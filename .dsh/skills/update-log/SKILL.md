# 每轮收尾：总结改动，并把程序改动累积进「预览版」更新日志（ShaoLu · AutoShaoLu 自动化烧录）

## 0. 定位与范围

- 发布文件：根目录 `更新日志.md`（**当前尚不存在，第一次需要记录程序改动时新建**）；**按版本分节**（标题 `## <版本号>`，如 `## 0.6`），新版追加在文件末尾，最新版在最下方。
- **版本号是四段**：`主.次.预览位.内部位`，当前为 `0.6.2.2610`。与 ORT一键报告的三段 `X.Y.Z` 不同，别照抄那边的号。四段含义与进位（**2026-10-13 用户确认**）：
  - `主.次`（0.6）——正式发布版本，由用户提出并指定（「发布 0.6」）。预览期间不动。
  - `预览位`（第三段，当前 2）——**功能计数**：预览期间每发生一次「这次改动值得算一次版本更新」就 +1（0.6.2 → 0.6.3）。它与正式版无关，只用于区分预览轮次。
  - `内部位`（第四段，当前 2610）——**内部构建序号，固定格式「年份后两位 + 月份两位」起头，之后递增**：2026-10 的号段是 `26xx`，当前值 `2610`（10 = 2026-10）。需要并列一个新号时按 `2611`、`2612`… 递增；跨月后新号段从「年月 + 1」起，如 2026-11 用 `2611`。
  - **每次预览改动都让「主.次.预览位.内部位」四段整体成为一个没出现过的号**：预览位 +1 时，内部位归到当前年月号（2026-10 → `0.6.3.2611`）；预览位不变时，内部位按上面的规则递增（`0.6.2.2610` → `0.6.2.2611`）。这样发布包名 `AutoShaoLu_<四段号>` 永不重复。
  - 发布包名与 exe 的 File/Product 版本都用这四个段；**程序界面目前不显示任何版本号**，所以号的唯一用途是标识发布包与程序集。
- **文件里同时存在两段状态**：
  - **正式版本**小节（`## 0.5`…）——用户已发布的版本，不再改动。
  - 末尾一个**预览版**小节（如 `## 0.6（预览版）`）——下一版本的**更新内容缓存**：正式版之后的所有程序改动都先累积在这里，逐轮追加；用户说「发布 0.6」时，这个小节整体成为 `## 0.6`。
- **版本号三处一致**（2026-10-12 用户决定统一，`tools/build-app.ps1` 每次构建都会校验，不一致直接报错）：
  1. `ShaoLu\ShaoLu.csproj` 的 `<ApplicationVersion>`（写**明确号**，如 `0.6.2.2610`，**不要 `%2a` / `*`** 自动位）；
  2. `ShaoLu\Properties\AssemblyInfo.cs` 的 `AssemblyVersion`；
  3. 同文件的 `AssemblyFileVersion`。
  改版本必须三处同时改。这是 **legacy 非 SDK 工程**：MSBuild 不会生成程序集版本特性（删掉 AssemblyInfo 里的声明会编出 `0.0.0.0`），所以无法让后两者从 csproj 自动派生。
- **主界面版本号显示**：本仓库现在**没有任何读取程序集版本并显示的代码**（`ShaoLu\Views\WindowAbout.xaml` 也没有版本行）。因此升版本号只改上面三处，**不要**为了显示版本去新增代码；用户明确要求「界面上显示版本」时才做。
- **发布包**：跑 `tools\pack-release.ps1`（Release 编译 → 过滤 pdb/ClickOnce 清单/WebView2 缓存/日志/用户数据 → 复制到 `ShaoLu\bin\publish\AutoShaoLu_<版本号>\`）。**默认只出目录、不生成 zip**，要 zip 加 `-Zip`；打包前确认没有 `ShaoLu.exe` 在运行。
- **只写程序更新内容**：AutoShaoLu（自动化烧录）的面向用户变化与影响运行的变化——新功能、行为/界面变化、程序缺陷修复、步骤文件（`.autostep`）格式与兼容性变化、数据结构/数据库/本机设置文件格式变化与迁移、破坏性变化（改名、路径调整、旧数据处理）。
- **不写实现细节**：不写文件名/类名/方法名/字段名，不写"代码清理""重构了 XX 类""新增单元测试""升级依赖""编译警告"这类与功能无关的条目，不写提交、构建与验证过程。
- **不写仓库协作类改动**：skill（`.dsh/skills/`）、`tools/` 构建与打包脚本、`.dsh/actions.json`、提交/推送流程、验证脚本、截图、调试产物、纯文档整理（`Readme.md` / `使用说明书.md`）——这些与程序运行无关，一律不进 `更新日志.md`（预览版小节同样不进）。
- `修改记录.md`：**本仓库历史变更记录，格式为「日期 + 类型 + 需求描述/原因分析/修改内容说明/涉及文件/构建验证结果」**，最新在最上方，**用法保持原样**——本技能不为它新增规则，也不改写、删除、重排它的既有内容。`更新日志.md` 是给用户看的面向功能日志，两者分工不同、不要互相复制。
- 与 skill `git-commit-sync` 的分工：`update-log` 负责**写内容**，`git-commit-sync` 负责**提交推送**。顺序固定为
  **汇总改动 → 累积到预览版（或转正发布）→ git-commit-sync（add → commit → push）**，
  保证更新日志进入本轮同一个 commit，不出现"日志留在工作区没提交"或"推送完再补一次"。
- 用户明确说「不要日志 / 先别提交 / 不要推送」时以用户指令为准。

## 1. 先确认本轮有没有改动

- 用 `git status --porcelain`（及 `git diff --stat`、必要时 `git diff --cached --stat`）拿到**真实**变更清单，不要凭记忆。
- 完全没有文件改动（且没有已暂存内容）→ 不写日志、不升版本号，最终回复写一行「本轮无文件变更，未提交」。
- 注意：构建产物、临时冒烟程序、日志文件若被 `.gitignore` 忽略，不算本轮改动。

## 2. 每轮有改动都要做的：总结「更新内容」

在本轮最终回复里给出简洁摘要（1~5 条），每条写"**改了什么 + 影响**"，例如
`- 步骤列表新增撤销/恢复：误删步骤后可一步回退，编辑单个步骤时改动也能回退`。
不写「优化了体验」「完善了细节」这类空话，也不要把只讨论过、没落地的内容写成已完成。

这一步只输出摘要，是否落盘由第 3 步决定。若本轮改动全是仓库协作类（技能/约定/脚本/文档），摘要里注明「非程序改动，不进更新日志」。

## 3. 判断本轮有没有【程序】改动

- **有程序改动**（代码、界面、资源、语言文案、数据结构、本机设置格式…）→ 走第 4 步：写进预览版小节 + 升预览号。
- **只有仓库协作类改动**（`.dsh/skills/`、`.dsh/actions.json`、`tools/` 脚本、`Readme.md` / `使用说明书.md` 等纯文档）→ **不写 `更新日志.md`、不升版本号**，第 2 步摘要里注明即可。
- **正式版本发布只看用户有没有主动提出**：用户没提，本轮就只做第 4 步的累积，绝不自作主张把预览版转正或新开版本号；用户提了（「发布 0.6」），走第 5 步。
- 判定存疑时问一句「这一轮要不要作为一次版本更新记进更新日志？」，不要硬发。

## 4. 累积到预览版（默认动作，每轮程序改动都做）

1. **读文件末尾**（用 read 工具），确认：最新正式版本号、预览版小节标题、该小节已有条目。
   - 文件里还没有预览版小节 → 新建 `## <最新正式版 + 0.1>（预览版）`，例如已发布 0.5 → `## 0.6（预览版）`；若上一正式版就是 0.6，则下一段是 `## 0.7（预览版）`。
2. **追加条目到预览版小节**（逐轮累积，**改上面的正式小节一个字都不许**）：
   - 本轮程序改动按「条目写法」（本步骤第 4 点）追加在预览小节末尾。
   - 同一功能的既有条目直接改写合并，不新增重复条目；多次演进只保留**最终形态**。
3. **预览版本号进位**（预览号是本仓库**唯一允许自动 +1** 的版本号；号是四段 `主.次.预览位.内部位`，语义见第 0 节）：
   - **大改动** → 预览位 +1、内部位归到当前年月号：`0.6.2.2610` → `0.6.3.2611`（2026-10；到 2026-11 则是 `0.6.3.2611` 起，新号段从「年月 + 1」开始）。
     判定（满足任一即算大改动）：本轮预览小节**新增条目 > 5 条**；或含**一整个功能**的新增/重构/推倒重做。
   - **小改动** → 预览位不动，内部位照旧规则递增：`0.6.2.2610` → `0.6.2.2611`。
   - **每个新号必须是四段都没出现过的新号**，发布包名 `AutoShaoLu_<四段号>` 才不会重复。
   - **起点**：上一正式版 + 0.1，如已发布 0.5 → `0.6.0.0`。一轮只升一次，同一轮内不重复升。
   - **三处同时改**（`tools/build-app.ps1` 下次构建会校验，改漏了直接构建失败）：
     - `ShaoLu\Properties\AssemblyInfo.cs` 的 `AssemblyVersion` 与 `AssemblyFileVersion`；
     - `ShaoLu\ShaoLu.csproj` 的 `<ApplicationVersion>` —— 写**明确号**（如 `0.6.2.2611`），**不要用 `%2a` / `*`**，自动位会和程序集版本漂移。
   - 升完版本可用 `powershell -NoProfile -File tools\build-app.ps1 -Configuration Debug` 快速验证三处一致（一行 `==> Version: ... (ApplicationVersion / AssemblyVersion / AssemblyFileVersion all match)`）。
4. **条目写法**：
   - `- **功能名**：一句话说明改了什么、用户会看到什么变化。` 一条一个功能。
   - 不写实现细节；不写日期；不写「已提交/已推送/验证通过」。
   - 措辞尽量短，纯可用性小改可并为一条「其他改进」。

## 5. 正式发布（用户提出时）

1. **版本号由用户指定**（「发布 0.6」→ `## 0.6`）。用户只说「这是一次版本更新」没给号 → 用用户措辞里的号；实在没有才问一句，**不要自行 +0.1**。
2. **预览小节转正**：把标题 `## 0.6（预览版）` 改成 `## 0.6`——去掉预览标记，**内容原样保留，条目一条都不删**。
3. **程序版本号归零为 `0.6.0.0`**，三处一致：`ShaoLu\Properties\AssemblyInfo.cs` 两处 + `ShaoLu\ShaoLu.csproj` 的 `ApplicationVersion`。
4. **打包**：跑 `powershell -NoProfile -File tools\pack-release.ps1`（默认只出目录、不生成 zip；要 zip 加 `-Zip`）。产物在 `ShaoLu\bin\publish\AutoShaoLu_0.6.0.0\`。打包前确认没有 `ShaoLu.exe` 在运行，否则 Release 输出被占用会失败。日志与版本号都改完后再打包。
   - 该脚本含中文注释，**必须保留 UTF-8 BOM**（write/edit 会去掉 BOM，改完要补回）。
5. 之后的新程序改动，重新从 `## 0.7（预览版）` 开始累积。

## 6. 收尾与汇报

- 写完日志立刻按 `git-commit-sync` 执行：暂存 → 中文 Conventional Commits 提交 → `git push origin <分支>`。commit message 以本轮功能为主，可在正文加一行说明已更新 `更新日志.md`（打了包时一并说明）。
- 最终回复固定给出一到两行结果，例如：
  - 累积：`本轮更新内容：…` + `已计入 0.6 预览版（更新日志.md 共 N 条）；程序版本号 0.6.2.1（三处一致）；已提交 <hash>，已推送 origin/master`
  - 发布：`本轮更新内容：…` + `已发布 0.6：预览小节转正、版本号三处归零为 0.6.0.0、发布包 ShaoLu\bin\publish\AutoShaoLu_0.6.0.0\；已提交 <hash>，已推送 origin/master`
  - 只有仓库协作类改动：`本轮更新内容：…（非程序改动，未进更新日志）` + 提交/推送结果
  - 无改动：`本轮无文件变更，未提交`

## 硬性约束

- 绝不编造未发生的改动；不把讨论、计划、待办写成"已完成"。
- `更新日志.md` 只写**程序功能与行为变化**：不写日期、不写实现细节（文件/类/方法/测试/构建/依赖）、不写技能与仓库约定类改动——预览版小节同理。
- **只允许自动升预览号**（默认内部位 +1；大改动时预览位 +1、内部位归到当前年月号）；正式版本号**由用户主动提出并指定**，不自行 +0.1、不按条目阈值自行转正。
- 版本号必须**三处一致**：`ShaoLu\ShaoLu.csproj` 的 `ApplicationVersion`、`ShaoLu\Properties\AssemblyInfo.cs` 的 `AssemblyVersion` 与 `AssemblyFileVersion`（`更新日志.md` 的版本标题与它们对应；构建时由 `tools\build-app.ps1` 校验）。
- **不改写、不删除已发布的正式版本小节**；用户明确要求「统一到某一版 / 整理更新日志」时才可以合并改写，且功能要点一条都不能丢。
- 写入前必须查重：同功能只保留一条、只保留最终形态。
- 不改写、不删除 `修改记录.md` 的既有内容，也不用本技能的规则去约束它。
- 用户没提出发布就不转正、不打包；不重复发布同一版。
- 更新日志与提交必须在同一轮内完成，不允许留到下一轮补。
- 不新建其他日志文件（`CHANGELOG.md` 等）。
